# Удалённый бэкенд ffmpeg — проект

**Дата постановки:** 2026-08-28.
**Заказчик:** владелец репозитория.
**Смежный проект:** служба конвертации видео (HTTP API к ffmpeg с кодированием
на NVENC), развёрнута и принята 26.08.2026. Её спека — раздел «Служба
конвертации» в документации того проекта; здесь она называется просто
«служба».

Скрипты `ffmpeg/` получают второй бэкенд вычисления: тот же `config.ini`, та же
оркестрация папок, но кодирование уезжает на серверную карту вместо локального
ffmpeg.

Спека службы называет наши скрипты своим вторым заказчиком и оставляет клиенту
всё, что касается файлов на его диске: выборку входов, зеркало подпапок, имена
выходов, карту коллизий, manifest, сводку `ok/fail/skip`. Служба — вычислитель,
а не оркестратор. Этот документ описывает клиентскую половину того же контракта.

## 1. Зачем

Локальный конвертер считает на процессоре рабочей машины. На серверной карте то
же 4K-перекодирование в HEVC идёт вчетверо быстрее (18.5 с против 4.5 с на
20-секундном отрезке по замерам службы), и карта на машине владельца для этого
не нужна вовсе.

Заменить скрипты службой целиком нельзя и не нужно: половина их работы — это
обход папок, имена и учёт готового, и всё это про файлы, которые лежат у
клиента. Поэтому не «переезд», а второй бэкенд под тем же `config.ini`.

## 2. Три решения, принятые до дизайна

| Вопрос | Решение | Почему |
|---|---|---|
| Форма | Прозрачный второй бэкенд внутри существующего конвейера | Один `config.ini` обязан давать один результат локально и удалённо. Отдельный инструмент рядом означал бы вторую реализацию оркестрации, которая разойдётся с первой — а паритет в этом репозитории проверяется тестами |
| Платформы | `.sh` + `.ps1` + GUI; `.cmd` предупреждает и считает локально | В cmd.exe нет ни нарезки файла по смещениям, ни `sha256`, ни разбора JSON. Санкционированный прецедент — `parallel_files` |
| Адрес и ключ | Переменные окружения через `${VAR}` в `config.ini` | Репозиторий публичный. Подстановка `${ENV_VAR}` уже есть во всех трёх читателях конфига — изобретать нечего |

## 3. Точка стыковки в коде

В [`FFmpeg_Converter_script.sh`](../../../ffmpeg/FFmpeg_Converter_script.sh)
удалённый путь подменяет **ровно один участок** `encode_file` — блок запуска
ffmpeg с прогресс-циклом (строки 984–1085 на момент написания). Всё, что до и
после, работает без изменений:

```
manifest_is_complete → пропуск                     ← не трогаем
проверка коллизий F12 (выход == вход)              ← не трогаем
цикл по частям разрезания, имена part.N            ← не трогаем
   ├─ dry_run: печать команды                      ← подменяем на план службы
   ├─ запуск ffmpeg + прогресс-бар → out_tmp       ← ПОДМЕНЯЕМ
   └─ валидация, mv out_tmp → out_file, сводка     ← не трогаем
manifest_write при успехе всех частей              ← не трогаем
```

Результат службы скачивается в тот же `partial_path` и переименовывается только
после той же проверки `-f null -`, что и локальный выход. Транзакционность
записи, поведение при Ctrl-C и содержимое `manifest` от смены бэкенда не
зависят.

`.ps1` и GUI получают то же самое в своих терминах.

### 3.1 Части разрезания остаются клиентскими

Служба умеет `op: split` и сама режет вход на N выходов. Мы этим **не
пользуемся**: границы и имена выходов назначал бы сервер, и их пришлось бы
натягивать на нашу схему `part.N` и на `manifest`, где каждый выход записан
своим путём и размером.

Вместо этого файл загружается **один раз**, а затем на каждую часть создаётся
своя задача `op: cut` с `reencode: true` (спека службы, раздел 4.3: при
`reencode: true` `cut` принимает весь набор полей `transcode`). Цикл по частям,
суффиксы, manifest и сводка остаются ровно теми же, что на локальном пути.
Определение границ тишины тоже остаётся локальным — оно уже написано,
оттестировано, и `GET /v1/uploads/{id}/silences` дал бы второй источник правды
для того же ответа.

Следствие: `op: split` в клиенте не используется вовсе.

## 4. `[remote]` в `config.ini` — пять ключей

```ini
[remote]
# Считать на сервере конвертации вместо локального ffmpeg (yes/no)
enabled = no
# Адрес API службы. Приватное значение — задаётся переменной окружения
endpoint = ${TRANSCODE_URL}
# Bearer-ключ службы — тоже переменной окружения
api_key = ${TRANSCODE_API_KEY}
# Где считать на сервере: auto (ждать карту, потом процессор), gpu, cpu
prefer = auto
# Сколько ждать окна на карте, секунды
wait_timeout = 1800
```

Значения `endpoint` и `api_key` в репозиторий не попадают: в файле стоят имена
переменных, значения приходят из окружения. Не заданы — подстановка даёт пусто
и печатает `WARN`, а `remote_preflight` (раздел 6) обрывает прогон с внятной
причиной.

**Все пять ключей читаются во всех трёх `run`-файлах.** Этого требует
[`tests/common/test_config_keys.sh`](../../../tests/common/test_config_keys.sh):
для `ffmpeg` действует полный трёхплатформенный паритет. В `.cmd` ключи
читаются, и при `enabled = yes` печатается `[ПРЕДУПРЕЖДЕНИЕ]` о том, что режим
там недоступен, после чего файлы считаются локально. В
[`tests/config-key-contract.yaml`](../../../tests/config-key-contract.yaml)
заводится исключение `sh_ps1_only_behavior` рядом с существующим
`sh_only_behavior`.

### 4.1 `prefer` против `[gpu] hw_accel`

`[gpu] hw_accel` управляет **локальным** путём и на удалённом не значит ничего:
какой карте считать на сервере, решает очередь службы. Авторитетен `[remote]
prefer`. Исключение — `hw_accel = intel`: Intel-карты на сервере нет, и об этом
печатается предупреждение, а не молчаливая подмена (то же решение принято на
стороне службы).

## 5. Отображение `config.ini` на операции службы

Уезжает на сервер только то, где выигрывает карта.

| Режим `config.ini` | Операция | Где считается |
|---|---|---|
| обычное перекодирование | `transcode` | сервер |
| `[split] start` и/или `length` | `cut`, `reencode: true` | сервер |
| `split_by_silence = yes` | `cut` на каждую часть (раздел 3.1) | сервер |
| `copy_codecs = yes` | — | **локально** |
| `extract_audio_copy = yes` | — | **локально** |
| `merge_files = yes` | — | **локально** |
| `create_frame = yes` | — | **локально** |
| `audio_only = yes` | — | **локально** |

Служба все эти операции умеет (`remux`, `extract_audio`, `concat`, `frames`,
`audio`), но ни в одной из них карта не участвует: там ffmpeg либо переливает
байты, либо считает на процессоре. Отправить три гигабайта по сети ради
`-c copy` — чистый проигрыш к локальному прогону. Каждый такой файл считается
локально, и в лог пишется строка о том, почему режим не уехал: молчание здесь
неотличимо от поломки удалённого пути.

### 5.1 Поля

| `config.ini` | Поле службы |
|---|---|
| `[video] codec` | `codec`: `libx264`/`h264_nvenc` → `h264`, `libx265`/`hevc_nvenc` → `hevc`, `libsvtav1`/`av1_nvenc` → `av1`, `h264_qsv` → `h264` + предупреждение |
| `[video] quality` | `quality` (служба принимает весь диапазон 0–51) |
| `[video] bitrate` | `bitrate` (кбит/с × 1000 → бит/с), плюс `bitrate_cap_source: true` — локальный скрипт тоже не поднимает битрейт выше исходного |
| `[video] resolution` | `resolution` |
| `[video] keep_aspect_ratio` | `keep_aspect` |
| `[video] framerate` | `fps` |
| `[video] rotation` | `rotate` |
| `[video] container` | `container` |
| `[video] subtitles` | `subtitles` + `subtitle_upload_id` (раздел 5.2) |
| `[audio] codec/channels/bitrate/sampling_rate/normalize` | вложенный объект `audio` |
| `[speed] playback_speed` | `speed` |
| `[gpu] preset/tune/rc` | `preset`, `tune`, `rc` |
| `[performance] threads` | `threads` (действует только на процессорном пути службы) |
| `[other] subtitles_style` | `subtitle_style` (служба разбирает строку по белому списку ASS и собирает `force_style` заново) |
| `[options] overwrite_existing` | `no_reuse: true` — отключает дедупликацию службы |
| `[other] dry_run` | `dry_run: true` |

`[folders]`, `[other] save_old_extension`, `format_files_in`, `enable_log`,
`log_file` остаются клиентскими: они про файлы и папки на нашем диске, о
которых служба ничего не знает.

`[performance] parallel_files` на удалённом пути **игнорируется с
предупреждением**: параллельность там задаёт очередь службы — одна задача на
карте, две на процессоре, — и запуск четырёх клиентских подоболочек не ускорит
ничего, зато сделает прогресс-вывод нечитаемым.

Незнакомое службе поле — отказ `400`, а не молчаливое игнорирование. Поэтому
маппинг обязан быть полным: поле, которое мы не отправили, тихо примет значение
по умолчанию службы, и результат разойдётся с локальным.

### 5.2 Субтитры

Локальный путь ищет `.srt`/`.vtt`/`.ass` рядом со входом и подставляет путь в
filtergraph. Служба путей в параметрах не принимает по построению: файл
субтитров приходит **той же дорогой, что видео** — загрузкой с проверкой
`sha256`, — а путь в фильтр подставляет и экранирует она сама.

Значит клиент при `subtitles = burn|meta` загружает найденный файл субтитров
вторым и передаёт `subtitle_upload_id`.

## 6. Модуль клиента: шесть функций

Новые файлы `ffmpeg/remote_client.sh` и `ffmpeg/remote_client.ps1`,
подключаемые из `FFmpeg_Converter_script.sh` / `.ps1` и из GUI. Отдельным
модулем, а не внутри `script.*`: те файлы уже по 78–80 КБ, и ещё пятьсот строк
сетевого кода сделали бы их нередактируемыми. Сетевой клиент — самостоятельная
единица со своим контрактом, её можно понять и протестировать отдельно.

Обе платформы дают одинаковый набор:

| Функция | Что делает |
|---|---|
| `remote_preflight` | `GET /v1/capabilities` один раз за прогон: жив ли сервер, есть ли нужный энкодер, совпадает ли `args_version`. Обрывает прогон **до первого файла** |
| `remote_op_for_config` | Из уже разобранных переменных конфига — операция и объект параметров. Чистая функция без сети: её и сверяет тест паритета SH↔PS1 |
| `remote_upload` | Кусками по объявленному службой `chunk_size`, `PATCH` с `Content-Range`, докачка с известного смещения после обрыва, `sha256` в `complete` |
| `remote_submit` | `POST /v1/jobs` → `job_id`; распознаёт ответ `reused: true` |
| `remote_wait` | Опрос `GET /v1/jobs/{id}`, кормит прогресс-бар и файл прогресса GUI |
| `remote_fetch` | `GET /v1/jobs/{id}/result` потоком в `partial_path` |

**Инструменты.** `.sh` — `curl`, `sha256sum` (с откатом на `shasum -a 256`),
`dd` для нарезки кусков. JSON разбирается минимальным экстрактором плоских
полей: **зависимости от `jq` быть не должно**, в Git Bash его нет.
`.ps1` — `System.Net.HttpWebRequest` с потоковым `FileStream`, `Get-FileHash`,
`ConvertFrom-Json`. Именно `HttpWebRequest`, а **не `Invoke-WebRequest`**: в
PowerShell 5.1 он буферизует тело ответа целиком в память, и результат на 3 ГБ
убил бы процесс.

Наличие `curl` проверяет `remote_preflight` — отсутствие инструмента должно
быть видно до первого файла, а не на сотом.

## 7. Прогресс, ожидание карты, отмена

`remote_wait` опрашивает `GET /v1/jobs/{id}` раз в две секунды и кормит те же
приёмники, что и локальный путь: `show_progress_bar` в CLI и файл прогресса в
GUI (через `<file>.tmp` + `File.Replace`, как сейчас).

Добавляются две вещи, которых у локального пути нет и быть не может:

- **Фаза загрузки.** На файле в 3 ГБ по сети это и есть долгая часть; без
  отдельного индикатора прогресс стоял бы на нуле минутами.
- **Состояние `waiting_gpu`.** Служба отдаёт `waiting_seconds` и `missing_mib`.
  Их надо показывать текстом: ожидание, о причине которого не сказано,
  неотличимо от зависания.

Отмена (Ctrl-C в CLI, Stop в GUI) шлёт `DELETE /v1/jobs/{id}` прежде чем выйти.
Иначе брошенная задача продолжит держать карту, ради вежливости к которой
служба и построена.

## 8. Отказы — громко, без тихого отката на локальный ffmpeg

**Preflight не прошёл** — нет адреса, нет ключа, сервер недоступен, в
`capabilities` нет нужного энкодера, нет `curl` — прогон обрывается до того, как
тронут первый файл, с указанием причины.

**Упал один файл** — обрыв сети, `failed` у задачи, `413`, `507` — файл
получает `fail` в сводке, пакет продолжается. Загрузка перед этим повторяется:
она возобновляемая, и разрыв на 90-м проценте трёхгигабайтного файла не должен
стоить всего файла.

**Автоматического отката на локальный ffmpeg нет.** На пакете в двести файлов
молчаливый переход на процессор рабочей машины неотличим от зависания и
отменяет ровно тот смысл, ради которого режим включали. Откат «карта →
процессор» уже существует **на стороне службы** через `prefer: auto` и виден в
статусе задачи; дублировать его третьим слоем на клиенте незачем.

**Дедупликация.** Локальный `manifest_is_complete` проверяется первым — если
файл уже готов на диске, в сеть не идём вовсе. Дальше работает дедупликация
службы по подписи задачи; `overwrite_existing = yes` отключает её через
`no_reuse: true`.

## 9. Холостой прогон — и он же первая задача реализации

При `dry_run = yes` и включённом удалённом бэкенде клиент шлёт
`POST /v1/jobs` с `dry_run: true` и печатает возвращённый **план** (служба
отдаёт список шагов, а не одну команду: длинный файл она режет, кодирует
посегментно, склеивает и отдельным проходом обрабатывает звук).

Спека службы называет это первой задачей нашего проекта: сверить холостой
прогон нашего скрипта с холостым прогоном службы на одном и том же
`config.ini`. Паритет службы проверялся против эталонов, снятых с логики наших
скриптов вручную, — живых скриптов на сервере нет. Расхождения сборщиков надо
увидеть на холостом прогоне, до того как поедут гигабайты.

Поэтому порядок работ: сначала `remote_op_for_config` и `dry_run`, сверка
цепочек фильтров профиль за профилем, и только потом загрузка, очередь и
скачивание.

## 10. GUI

Новая группа «Сервер» в
[`FFmpeg_Converter_run_win_v18.ps1`](../../../ffmpeg/FFmpeg_Converter_run_win_v18.ps1):
галка «Считать на сервере», выпадающий `prefer`, поле `wait_timeout`, а также
поля адреса и ключа (ключ — под `UseSystemPasswordChar`).

> **Правка от 2026-08-29.** Первая редакция этого раздела запрещала
> редактировать адрес и ключ из GUI: «GUI сохраняет свои значения в
> `config.ini`; дай он редактировать эти два поля — приватные значения
> оказались бы в файле, который лежит в публичном репозитории». Обе посылки
> оказались ложными, и вывод вместе с ними. GUI **не переписывает**
> `config.ini` (паритет с GUI yt-dlp, где записи конфига тоже нет), а сам
> `ffmpeg/config.ini` **не лежит в репозитории** — он gitignored, в дерево
> закоммичен только `config.ini.example`. Приватность обеспечивают gitignore,
> маскировка поля ключа и барьер `tests/common/test_guardrails.sh` (suite
> «приватность»), который отдельно проверяет, что шаблон отслеживается, а
> рабочий конфиг — нет.
>
> Раздел приведён к реальности намеренно, а не помечен «историческим»: эта
> спека остаётся единственным документом с контрактом HTTP (пути `/v1`, поля
> ответов), и заведомо неверный раздел обесценивал доверие к остальным.

Итоговое поведение: значения полей берутся из `config.ini` при старте формы
(там же работает подстановка `${TRANSCODE_URL}` / `${TRANSCODE_API_KEY}`),
редактируются пользователем и передаются в запуск как есть. Обратно в файл
ничего не пишется — правка конфига остаётся ручной.

`api_key_command` и `on_failure` своих полей в форме не имеют сознательно:
первая может спросить пароль у менеджера, вторая меняет политику отказов —
обеим место в `config.ini`, а не в галочке, которую поставили один раз и забыли.
GUI их читает и передаёт в запуск.

В строке состояния показывается состояние задачи, включая ожидание карты и
подпись фазы (`отправка` / `ожидание карты` / `кодирование` / `скачивание`).

## 12. Что осознанно не делается

| Не делаем | Почему |
|---|---|
| Удалённый `merge`, `frames`, `audio`, `remux`, `extract_audio` | Карта в них не участвует; сеть дороже локального счёта |
| `op: split` службы | Имена и границы выходов назначал бы сервер; наш цикл по частям делает то же и уже покрыт тестами (раздел 3.1) |
| Автоматический откат на локальный ffmpeg | Молчаливый переход на процессор неотличим от зависания (раздел 8) |
| Удалённый бэкенд в `.cmd` | В cmd.exe нет нарезки по смещениям, `sha256` и JSON |
| Редактирование адреса и ключа из GUI | GUI пишет `config.ini`, репозиторий публичный |
| Параллельная отправка нескольких файлов | Параллельность задаёт очередь службы: одна задача на карте, две на процессоре. `parallel_files` на удалённом пути игнорируется с предупреждением |
| Зависимость от `jq` | Его нет в Git Bash, а Windows — основная платформа владельца |

## 13. Риски

**Антивирус.** `.ps1` компилируется в EXE через ps2exe, и мы добавляем туда
сетевые загрузки с потоковой записью файлов на диск — ровно тот класс
поведения, за который Kaspersky заблокировал `yt-dlp` v17. После сборки EXE
обязательна проверка запуска на машине с антивирусом; без неё работа не
считается завершённой.

**Расхождение сборщиков argv.** Служба поднимает `ARGS_VERSION` при правке
своего сборщика аргументов; наш маппинг об этом не знает. `remote_preflight`
сверяет `args_version` из `capabilities` с записанным у нас и при расхождении
печатает предупреждение: молча получить файл, собранный другой логикой, хуже,
чем шумно.

**`-ss` при прожиге субтитров.** Локальный путь при `sub_burned` и ненулевом
старте ставит `-ss` на **выход**, иначе фильтр `subtitles` видит обнулённые PTS
и титры съезжают. Делает ли служба эквивалентное в `op: cut` с `subtitles:
burn` — неизвестно; это первое, что надо сверить холостым прогоном (раздел 9).
Если нет — вопрос уходит на сторону службы, а не обходится на клиенте.

**Сеть — новый класс отказов.** У локального пути отказ детерминирован; у
удалённого появляются таймауты, обрывы на 90-м проценте и наполовину принятые
загрузки. Возобновляемость загрузки — не удобство, а условие работоспособности
на файлах в единицы гигабайт.

**Объём.** Два модуля по 400–500 строк, около 150 строк правок в каждом
`script.*`, около 200 в GUI, четыре тестовых файла, правки конфига и контракта.

## 14. Приёмка

1. **Холостой прогон совпадает.** Профили, снятые с `config.ini` (поворот,
   letterbox, скорость 1.75, нормализация, прожиг субтитров), дают на клиенте и
   в плане службы одни и те же цепочки фильтров в одном порядке.
2. **Один файл проходит целиком.** Загрузка, задача, скачивание, валидация
   `-f null -`, переименование, `manifest`. Результат воспроизводится локальным
   прогоном с точностью до параметров кодирования.
3. **Разрезание сохраняет имена.** Части `part.N` на удалённом пути называются
   ровно так же, как на локальном, и `manifest` перечисляет их все.
4. **Докачка работает.** Обрыв на середине загрузки, повтор — файл принят,
   `sha256` совпал, повторно залиты только недостающие куски.
5. **Отказ preflight обрывает до первого файла.** Нет ключа, нет адреса,
   сервер недоступен — ни один файл не тронут, причина названа.
6. **Отказ одного файла не рушит пакет.** Пакет из трёх файлов, у среднего
   задача падает: два `ok`, один `fail`, сводка честная.
7. **Отмена освобождает карту.** Ctrl-C и Stop в GUI приводят к `DELETE`, и
   `GET /v1/jobs` показывает задачу отменённой.
8. **Ожидание объяснимо.** При занятой карте показывается, сколько уже ждём и
   сколько памяти не хватает.
9. **Локальные режимы остаются локальными.** `copy_codecs`, `merge_files`,
   `create_frame`, `audio_only`, `extract_audio_copy` при `enabled = yes` идут
   локально, и лог говорит почему.
10. **`.cmd` предупреждает.** `enabled = yes` даёт `[ПРЕДУПРЕЖДЕНИЕ]` и
    локальный счёт; ключи читаются, контракт-тест зелёный.
11. **Приватного в репозитории нет.** Ни адреса, ни ключа ни в одном
    коммитимом файле; guardrail-тест это проверяет; pre-commit hook проходит.
12. **EXE запускается.** Собранный ps2exe GUI стартует на машине с
    антивирусом.
